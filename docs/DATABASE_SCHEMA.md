# PostgreSQL Schema Design

This is the concrete relational design for the FastAPI/SQLAlchemy application. It specifies PostgreSQL tables and constraints but is not ORM, migration, endpoint, or application code. All monetary fields use `numeric(18,2)` unless a later verified requirement needs more precision; no authoritative field uses `real` or `double precision`.

## Conventions

- IDs are `uuid` primary keys. `gen_random_uuid()` is the proposed database default unless a later migration standard replaces it.
- All UTC timestamps are `timestamptz`; accounting/business dates are `date`; Bikram Sambat input is stored separately as `varchar(16)` only where retained for display/audit.
- Every school-owned table has `id uuid not null`, `school_id uuid not null`, `created_at timestamptz not null`, and its declared primary key `PRIMARY KEY (id)`. It also has `UNIQUE (school_id, id)` so a dependent can use a composite tenant-safe foreign key.
- All school-owned tables have `FOREIGN KEY (school_id) REFERENCES schools(id)`. A dependent school-owned FK is written as `(school_id, parent_id) REFERENCES parent_table(school_id, id)`.
- `created_by_membership_id` and mutable records’ `updated_at`/`updated_by_membership_id` are added where attribution is required. These are composite tenant FKs to `school_memberships`. System-owned tables use `created_by_user_id` where needed.
- `status` values use constrained `varchar` check constraints initially; PostgreSQL enums remain undecided because values will evolve with workflows. Locale values use standard identifiers; initial supported locales are `en` and `ne`, with later additions supported by registry data rather than schema changes.
- Table behavior is classified as: **immutable from insertion** (no routine `UPDATE`/`DELETE`); **mutable until terminal** (authorized updates only until a terminal status, then immutable); or **ordinary mutable** reference/projection data. PostgreSQL triggers and restricted database roles enforce the first two categories.
- Hashes such as `result_hash`, `entry_hash`, `content_hash`, `request_fingerprint`, and `snapshot_hash` are integrity/deduplication aids only. They use non-unique indexes where lookup is useful; operation and business uniqueness come from declared idempotency keys and business identifiers.
- Effective-period exclusions use PostgreSQL `daterange` plus the `btree_gist` extension. A null end date represents an open-ended range. Published/active versions with exactly one applicable value must not overlap; deliberately contextual alternatives use distinct keys or an explicit context discriminator.

## Tenant-safe foreign keys

Every tenant parent exposes `UNIQUE (school_id, id)`. Every child stores `school_id` and references a tenant parent using the pair, so a child cannot point at a same-shaped ID from another school. This includes `bank_accounts → school_ledger_accounts`, bank statements/reconciliations → bank accounts, and reconciliation items → posted journal lines. System reference FKs such as `rule_set_version_id`, `account_code_version_id`, `ledger_account_definition_id`, `official_template_version_id`, `users.id`, and `permission_presets.id` are global and read-only inputs. Generic links for evidence, lifecycle, decision evidence, and audit targets cannot use a single ordinary foreign key; their target table/type must be validated by an application service or database trigger, with the same `school_id` required before link creation. Splitting high-risk generic links into typed link tables remains an unresolved refinement.

## Localization and language-neutral accounting data

Initial standard locale identifiers are `en` and `ne`; `supported_locales` is extensible. Locale selection falls back from membership preference to user preference to school default to system fallback (`en`). School/user/membership preferences and UI formatting affect presentation only. Statuses, document types, codes, amounts, accounting dates, and journal semantics remain canonical and language-neutral; translated strings are never accounting authority. User-entered names and descriptions remain exactly as entered and do not need duplicated locale columns.

System-controlled localized reference text uses normalized translation records keyed by the canonical record and locale, particularly `account_code_version_translations`, `ledger_account_definition_translations`, and `permission_preset_translations`. Each references the canonical system record and `supported_locales`; translations supply display fields only and cannot create a second accounting identity. Do not duplicate rule sets, account codes, or ledger definitions for language variants. Keep four concerns distinct: UI translations, reference-data translations, user-entered text, and official printable template language. Preserve `official_template_versions.language` so English and Nepali Forms 1–40/report templates render the same underlying financial data. Nepali calendar handling (including Bikram Sambat conversion) is independent of Nepali-language localization.

## Immutable history and transaction behavior

Immutable-from-insertion tables are: `platform_audit_events`, published rule/code/template versions, journal entries/lines, correction links, finalized evidence versions/links, lifecycle events, authorization decisions, audit events, and issued output archives. `inventory_movements` are immutable when inserted as posted movement history. Mutable-until-terminal tables include `receipt_issues`, `posting_requests`, `idempotency_records`, `projection_runs`, workflow documents, and generated outputs. Ordinary mutable tables include school/reference metadata and rebuildable projection rows. PostgreSQL triggers plus a restricted database role enforce these categories.

The application service creates a post in one transaction: verify tenant/membership/authorization and document state; resolve effective rule/code versions from accounting date; derive with the pure domain core; insert posting request/result, journal entry/lines, and idempotency record; transition the document to Posted/Locked; execute the mandatory deferred journal-balance constraint trigger; then enqueue or refresh projections. Any failure, including a journal with no lines or unequal totals, rolls back all authoritative writes.

`document_sequences` uses a row locked by `SELECT … FOR UPDATE` during number allocation, incremented in the same transaction that creates the document. Receipt number allocation additionally locks its receipt-book control and inserts one `receipt_issues` row. Business-number uniqueness always includes `school_id`, fiscal year where applicable, document kind, and number. Exact reservation, gap, void, and reissue policy remains unresolved except where the verified manual specifies cancellation retention.

## Database versus domain-layer invariants

PostgreSQL enforces: primary/foreign keys, composite tenant scope, uniqueness, numeric/date/value checks, one school fund, document/receipt serial uniqueness, effective-period exclusion constraints, immutable/terminal-state triggers, simple journal-line shape, and a mandatory deferred constraint trigger requiring every finalized journal entry to contain lines whose total debits equal total credits.

The application/domain layer enforces: workflow eligibility, permission presets and authority evidence, self-approval policy, joint-signature evidence, effective rule selection, account semantic mapping, deterministic posting derivation, prohibition of duplicate business effects beyond idempotency keys, reconciliation matching, projection rebuild behavior, and form completeness. The pure Accounting Engine receives facts and versions and derives entries; callers never persist caller-authored authoritative debit/credit lines.

## Unresolved schema decisions

- The exact schemas for `jsonb` facts/context fields, which form fields become normalized columns, and typed link-table replacement for generic links.
- PostgreSQL Row Level Security as defense-in-depth, platform-admin user lifecycle, and authentication provider claims.
- PAN/identity validation, encrypted storage/redaction of bank and tax identifiers, and external-import synchronization.
- Exact fiscal close/reopen policy, sequence reservation/gap behavior, and maximum monetary/quantity precision where a verified rule requires it.
- The complete ledger-account taxonomy, rule mapping expressions, template rendering storage, projection refresh cadence, retention/legal-hold policy, and database role design for immutable triggers.
